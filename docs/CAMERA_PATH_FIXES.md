## Issues Fixed

### 1. ✅ Rotate-Around: 333 Frames Causes Too Much Movement at Loop

**Problem:**
- At 333 frames, the rotate-around preset was creating **2.77 full orbits** instead of 1
- Hardcoded `frames_per_loop = 120` meant the camera would complete multiple rotations in a single video
- This made seamless looping impossible

**Solution:**
- Added `closed_loop` parameter that automatically sets `frames_per_loop = num_frames` when `True`
- Now generates exactly **1 complete orbit per video length** for seamless looping
- When `closed_loop=False`, uses 120 frames per orbit for more visible rotation (useful for non-looping videos)

**File:** `deforum/utils/spline_camera_path.py:303-311`

---

### 2. ✅ Look-At Mode Was Hardcoded (No User Control)

**Problem:**
- Look-at behavior was hardcoded to `"blend"` mode with `0.3` blend factor
- Users couldn't choose between different camera behaviors:
  - `"center"` - Look at fixed center (legacy, causes drift)
  - `"tangent"` - Look forward along curve (POV roller coaster)
  - `"inward"` - Look at local curve center (tennis ball seam)
  - `"blend"` - Adaptive mix (was hardcoded default)

**Solution:**
- Exposed all 4 look-at modes as UI dropdown in Camera Path tab
- Added `look_at_blend` slider (0.0-1.0) to control blend amount
- Default remains `"blend"` mode at `0.3` (30% inward, 70% tangent)

**Files:**
- UI: `deforum/ui/tabs/tab_camera_path.py:147-183`
- Handler: `deforum/ui/handlers/camera_path_generator.py:722-754`

### 3. ✅ rotation_factor=-8.0 Was Never Actually Used!

**Problem:**
- Empirically validated `rotation_factor=-8.0` (from ORBIT_TESTS.md) existed in:
  - ✅ Documentation
  - ✅ Test code
  - ✅ Tuning Lab UI
- But it was **NEVER passed to preset generation**!
- Presets used a completely different quaternion-based system

**Solution:**
- Added `rotation_mode` parameter with two options:
  - `"quaternion"` (default) - Geometric look-at using quaternions (natural, adaptive)
  - `"empirical"` - Use `rotation_factor` formula (validated optimal = -8.0)
- Users can now choose between:
  - **Quaternion mode**: Natural camera behavior, adaptive to curve sharpness
  - **Empirical mode**: Tested optimal counter-rotation formula from tuning tests

**Formula (Empirical Mode):**
```python
rot_y = degrees(angle) / rotation_factor
# Example: 360° orbit with factor=-8.0 → 45° counter-rotation
```

**Files:**
- Core logic: `deforum/utils/spline_camera_path.py:344-371`
- UI controls: `deforum/ui/tabs/tab_camera_path.py:147-183`

## About Custom Splines vs Presets

**Your observation is correct** - they ARE mostly redundant!

### Current Architecture:
- **Presets**: Hardcoded control point generation → `generate_camera_path()`
- **Custom Splines**: User control point selection → same `generate_camera_path()`

### The 90% Overlap:
Both systems call the same underlying spline interpolation function. The only difference:
- **Presets**: Control points generated by preset algorithms
- **Custom**: Control points generated by pattern selection (circle/figure-8/random/line)

### Why Keep Both (For Now):
1. **Presets** provide quick, known-good results with minimal configuration
2. **Custom** allows advanced users to fine-tune control point placement
3. Different rotation calculation methods:
   - Presets: Type-specific (rotate-around uses look-at, street uses zero, etc.)
   - Custom: Always uses tangent-based if `look_at_curve=True`

### Potential Future Unification:
Could make presets act as **starting templates** that users can then customize:
1. User selects preset (e.g., "rotate-around")
2. System generates control points
3. User can optionally edit control points before generation
4. Single unified pipeline

**Recommendation:** Keep as-is for now. The current dual system works, and users who want quick results use presets while advanced users use custom splines. Unification would be a larger refactor with uncertain user benefit.

## UI Changes Summary

**Rotation Control Section:**
1. **Rotation Mode** (dropdown)

   - Adapts up to 0.8 on sharp curves

## Known Limitations

1. **Sphere mode wobble**: Even with `closed_loop=True`, first/last positions won't be pixel-perfect due to sinusoidal elevation wobble. Distance ~10 units is acceptable for 100-unit radius orbit.

2. **Empirical mode is 2D**: Empirical rotation only calculates Y-axis rotation (horizontal). X and Z rotations are zero. Quaternion mode calculates full 3D rotation.

3. **Custom splines don't support rotation_mode yet**: Only presets have the new rotation mode selection. Custom splines always use tangent-based rotation if `look_at_curve=True`.
